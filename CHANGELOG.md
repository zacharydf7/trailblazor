# Changelog

Trailblazor hasn't had a release yet. Until it does, two lists below run by date, newest first: renamed and removed
public API, and changes to markup and behavior that tests, styles or scripts can depend on. After the first release
they run by version. The docs site's Upgrading page is built from both.

### Markup and behavior

#### 2026-11-22

- A dialog opened through `IDialogService` is now canceled when the app goes to another page in place, by a link, from code or with the browser's Back button. Before, it stayed open over the new page, since its host is in the layout. It closes as from code, so its caller gets a canceled result and nothing asks whether it may be dismissed. A change of only the query string or the fragment leaves it open. To keep a dialog across pages, set `CloseOnNavigation = false` in its `DialogOptions`, or, for every dialog, `Dialogs.CloseOnNavigation = false` in `AddTrailblazor`. A `TbDialog` in markup is not affected.
- In `TbMentionInput` and `TbRichTextEditor`, text typed after Enter or Tab while newer suggestions or slash commands are on their way no longer drops the choice. Keys count in the order pressed: the suggestion goes in, or the command runs, once the list arrives, and what was typed in the meantime comes after it, with the caret after that text. Before, a quick `@ad`, Enter, ` said` over a slow connection left `@ad said` as text. Changing the mention or command being typed, moving the caret back into it or leaving the field still drops the waiting choice, as does a list that comes back empty. In the editor, so does the caret leaving the paragraph, as a second Enter makes it.
- `TbRichTextEditor` has slash commands. With `SlashCommands`, a slash typed at the start of a word opens the list that mention suggestions use, with the kinds of block the toolbar has buttons for, a horizontal line and a table, and then the app's own `Commands`, each a new `RichTextCommand` with `Text`, `Description`, `Keywords`, `Html` and `OnChosen`. Off by default. The list's part is still `mention-list`, and the options object the editor hands its script now has `slash`.
- The list of slash commands leaves out what can't apply where the slash is: the kind the block already is, and every kind of block in a table's cell. In a heading, quote or list item it starts with a Paragraph command, whose name is the new string `RichTextEditor.Paragraph`, which `RichTextEditorLabels.Paragraph` replaces. A command's `Html` goes in with its text joining the line and a heading, quote or list starting under it. Both testing kits have `RichTextEditor(label).SlashCommandAsync(typed, command)`.
- `TbRichTextEditor` has find and replace. `ShowFind` adds a Find and replace button to the toolbar (`data-part="find-toggle"`) and takes Ctrl+F (Cmd+F) while the editor has the focus, opening a bar (`data-part="find"`) that marks the matches as CSS highlights, steps through them and replaces one or all. Its words are thirteen new strings, from `RichTextEditor.FindAndReplace` to `RichTextEditor.Replaced`, which `RichTextEditorLabels` replaces. Off by default.
- `TbRichTextEditor` has a toolbar over the selection. `ShowFloatingToolbar` shows a popover (`data-part="floating-toolbar"`) over selected text, with the character formats and the link button, and `FloatingFormats` narrows them. Its name is the new string `RichTextEditor.FloatingToolbar`, which `RichTextEditorLabels.FloatingToolbar` replaces. Off by default.
- `TbRichTextEditor` takes marks of the app's own. `Marks` lists them as `RichTextMark`s, each with a toolbar button and an optional `Shortcut`; a mark named `cite`, `dfn`, `kbd`, `q`, `samp` or `var` is written as that element, and any other as `<span data-tb-mark="name">`. `RichTextRun.Marks` holds a run's marks, which its constructor takes, as does the new `RichTextRun(Mention, RichTextFormats, Tone?, IEnumerable<string>)`; code that rebuilds runs, such as a `TransformPaste`, passes them on or they are dropped. `RichTextSchema.Marks` names the ones to keep when reading. The options the editor hands its script now have `marks` and `shortcuts`.
- `TbRichTextEditor` takes kinds of block of the app's own. `CustomBlocks` lists them as `RichTextBlock`s, each with a toolbar button, a slash command and an optional `Shortcut`; a paragraph of the kind is written as `<p data-tb-block="name">`. `RichTextParagraphKind` has a new member, `Block`, so a `switch` over the kinds needs a case for it; `RichTextParagraph.Block` names the kind, which the new `RichTextParagraph(IEnumerable<RichTextRun>, string)` takes. Code that rebuilds a paragraph from its `Kind`, such as a `TransformPaste`, must use that constructor for a `Block` (the one that takes a kind throws for it) or call the new `RichTextParagraph.WithRuns`, which gives a paragraph of the same kind, level, cell and block with other runs. `RichTextSchema.CustomBlocks` names the ones to keep when reading. A mark and a block can't share a name: the editor throws. The editor's script gets these kinds in the `blocks` option and their keys in `shortcuts`. bUnit's `SlashCommandAsync` now keeps the app's marks, blocks and mentions in a command's HTML, as the browser does.
- `TbRichTextEditor` has text color. `RichTextFormats.Color` adds a Text color menu to the toolbar (`data-part="color-menu"`) with the design system's tones and Default, and `RichTextRun.Color` holds a run's tone. In the value a color is `<span data-tb-color="danger">`, around the format tags and inside the link, and the library's style sheet now colors `[data-tb-color]` wherever it is on the page. It is on by default, like the other formats: an editor that takes the default `Formats` shows the new menu, and such a span in a value or in pasted text is kept. Set `Formats` without `Color` to leave it out. A color from a style isn't read. The menu's words are the new strings `RichTextEditor.TextColor`, `RichTextEditor.DefaultColor` and `RichTextEditor.ColorPrimary` through `ColorInfo`, which `RichTextEditorLabels` replaces. `RichTextRun`'s constructor takes a `color` after `link`, a new constructor takes a mention with a color, and a colored run's `Formats` includes `RichTextFormats.Color`, as a linked run's includes `Link`. So code that builds a run from another's `Formats` has to pass its `Color` too, or take the `Color` flag off: the constructor throws for the flag without a color, as it does for `Link` without a link.
- `TbRichTextEditor` has a highlight format, `RichTextFormats.Highlight`, written as `<mark>` inside the other formats, with a toolbar button and Ctrl+Shift+H (Cmd on macOS). It is on by default, like the other formats: an editor that takes the default `Formats` shows the new button, and a `<mark>` in a value or in pasted text is kept, where it used to become plain text. `RichTextDocument.Parse` with the default schema keeps it too. Set `Formats` without `Highlight` to leave it out. The button's name is the new string `RichTextEditor.Highlight`, which `RichTextEditorLabels.Highlight` replaces.
- `TbDockPanel` has `KeepWindowFor`, for a panel that comes and goes, such as a form that is there only while a task runs. When the app takes such a panel away while it shows in a browser window of its own, the window stays open for the time `KeepWindowFor` gives, says that the panel isn't open, and shows the panel again when the app makes it again, with no click. The message is a `status` with `data-part="empty-window"`, and its text is the new string `Dock.EmptyWindow`, which `DockLabels.EmptyWindow` replaces. Without `KeepWindowFor` nothing changes: the window closes with the panel.
- A dock panel's own browser window says when the page has lost its connection to the server, since Blazor shows that on the page only: a notice with `data-part="connection-lost"` and the role `alert` covers the window, and what the window holds is inert until the page has reconnected. The text is the new string `Dock.ConnectionLost`, which `DockLabels.ConnectionLost` replaces, and the dock's root carries it in `data-connection-lost` when `AllowPopOut` is on and the dock runs on the server. An app with its own `reconnectionHandler` tells the dock by sending `components-reconnect-state-changed` on `document`, with `detail.state` set to `show` and later to `hide`. A panel whose window is closed while the connection is lost now shows in the dock again once the page has reconnected; before, it stayed hidden until it was returned from the row of panels in their own windows. A panel's window also closes when the page comes back on a new circuit, where it used to stay open with a panel nothing drew.
- A dock panel's browser window opens where the panel's last one was, at that size, and no longer over the dock each time. The dock notes each window's place and size while it is open and keeps them for the browser session, or beside the saved layout when the dock has a `PersistenceKey`. The dock's root has `data-persistence-key` when it has one.
- `TbTreeView` has `PrerenderKey`, as the data grid does. On a prerendered page, a row that starts open with `LoadChildren` loads its children twice, while prerendering and again once interactive, and shows a loading row in between. With a key, the tree keeps the prerendered children with the page and takes them as loaded, so each row loads once and its children stay put, on the server or in WebAssembly. The items must write to JSON and read back, a parent's key must come out the same afterward, and each tree on a page needs its own key. Without a key nothing changes.
- `TbRichTextEditor` suggests mentions. With `MentionTriggers` and a `MentionSearch` function or `MentionItems`, typing a trigger such as `@` at the start of a word opens a list of suggestions under it, with the mention input's keys: Up and Down move, Enter or Tab chooses, Escape closes the list until the text changes. A choice goes in as a mention with a space after it. `OnMentionsChanged` gives the mentions in the text when the user's edit changes them, and `OnMentionSearchFailed` gets the exception when a search fails. `MaxMentionItems` and `MentionItemTemplate` shape the list, and `RichTextEditorLabels` has `MentionSuggestions` and `MentionSearchFailed` for what is read out. The editor has two new parts, `mention-list` and `mention-caret`. Its editing area also counts in `data-sends` the values its script sends, and in `data-sends-answered` the ones the app has finished with. Both testing packages have a new `MentionAsync` helper that mentions an item in a test, and the Playwright one waits until those two counts match. The list of suggestions, here and in `TbMentionInput`, has `aria-busy` while a search is on its way.
- `RichTextDocument` and `TbRichTextEditor` can keep mentions. A `RichTextRun` can be a `Mention`: one run whose text is the trigger followed by the item's text, which never joins its neighbors and can't be a link. HTML reads and writes it as `<span data-mention="id" data-trigger="@">@Name</span>`, `RichTextDocument.Mentions` lists a document's mentions in order, and markdown writes one as its text. In the editor a mention is one unit: the caret doesn't go inside it, the arrow keys cross it in one step, Backspace and Delete remove it whole, and text typed beside it stays outside. Mentions are off by default, since other editors write `data-mention` too: set `RichTextSchema.Mentions` to read a document with them, and `MentionTriggers` on an editor. Elsewhere a `span` with `data-mention` reads as its text, as it always has.
- The lists that leave a resting pointer alone (`TbSelect`, `TbMultiSelect`, `TbAutocomplete`, `TbCascader`, `TbCommandPalette` and `TbMentionInput`) now keep the pointer's place for each kind of pointer and each window. A move by another kind of pointer, such as a finger on the screen while the mouse rests, used to make the browser's next move over a scrolled list count as the user's, and the option under the resting pointer took over from the keys. The same went for a move in another of the app's windows, which matters where each window has a pointer of its own, as in a browser test. Only the first move a kind of pointer makes in a window still counts as the user's, whoever sent it.
- A `TbDockManager` panel's own browser window now applies an alternate style sheet that a script turned on, even when the sheet's `media` only matches on the page after the window opens. In Chromium-based browsers and Safari, a sheet whose media didn't match as the window opened was taken as off for good, so when the media matched later the page applied the sheet and the window didn't.
- `TbDataGrid` has `PrerenderKey`. On a prerendered page, a grid with a `DataProvider` and no `Virtualize` asks for its first page twice, while prerendering and again once interactive, and shows its loading row in between. With a key, the grid keeps the prerendered rows with the page and shows them as it turns interactive, so the provider is asked once and the rows stay put. It works when the page turns interactive on the server or in WebAssembly. The rows must write to JSON and read back, and each grid on a page needs its own key. Totals aren't kept, so a grid with an `Aggregate` column asks once more for them, with the rows in view. Without a key nothing changes.
- `TbFocusScope` has `Blocking`: while such a scope is there, everything outside it is inert, as under a modal dialog, in its own window and in the app's other windows. In its own window each held element is marked `data-tb-blocked` and dims (`--tb-blocked-opacity` sets how much); the other windows dim under a scrim, as they do for a dialog. It's for content that has to be finished or dropped before anything else, where a dialog doesn't fit, such as an editor in a dock panel. Toasts, dialogs and the popups `DialogSettings.OutsidePopups` names stay usable, with two such scopes the newer one is in force, and a scope that can't be reached, such as one in a dock panel behind another tab, holds nothing until it shows. A `Trapped` scope's trap now stands down while the scope is inert or behind a modal dialog, so Tab works in a dialog that a trapped scope's content opens, where it used to do nothing. A focus scope's element now also gets `data-ready` once its script manages the focus.
- Two fixes for a `TbDockManager` panel's own browser window. Two panels opened in quick succession, before the page had answered for the first, now each get their own window: the second click used to close the first window, and the dock moved only the last panel asked for. A double click on one group's item opens that panel's window once, and no longer says the browser blocked a window for the group's next panel. The Open in new window item carries `data-pop` with its panel's element id for this. And a window that closed because the page took more than ten seconds to answer the click is no longer said to be blocked by the browser: screen readers hear "The new window for Notes closed before the panel was ready. Try again." (`DockLabels.PopOutLapsed`, `TbStrings.DockPopOutLapsed`).
- The bUnit helpers in `Trailblazor.Testing` follow `aria-labelledby` when they work out a control's name, as the Playwright helpers and a browser do: the named elements' text, in the attribute's order, comes before an `aria-label` and the control's own text. A field with no label is found by any one of the elements its input's `aria-labelledby` names, as Playwright's `GetByLabel` finds it. A test that found a control by its own text while an `aria-labelledby` named it otherwise needs the name a screen reader hears. When no button, link or field has the name asked for, the message now lists the names that are there, up to a dozen.
- A tree item template's text marked `data-part="text"` keeps the row's ellipsis and a filter match's weight inside wrappers of its own at any depth, down to a tree inside the row, whose rows are its own. It used to work straight in the template or in one wrapper, and text two wrappers deep made the row overflow. The deeper wrappers use `@scope`, so a browser without it keeps the one wrapper.
- A `TbTabs` panel's tab stop is decided again when text fills in or empties before the panel's first control, as when a heading loads after the panel has rendered. The script watched for added and removed elements but not for text that changes in place, so such a panel kept the stop it had, and a heading that arrived late couldn't be reached with Tab.
- A `TbDockManager` panel that comes back from a browser window of its own now goes back where it was docked, instead of staying in the floating window the layout kept for it. When nothing else in the layout has changed, the layout is the one the panel left, sizes and all. Otherwise a panel from a strip goes back to its strip, a panel that shared a group goes beside the nearest tab that was next to it, and one that had a group to itself gets that group back, at its size, on its side of what was next to it; with no neighbor left it stays floating. This holds for the Return button, a closed window, `ReturnAsync`, a window the browser refused, a panel whose `AllowPopOut`, or the dock's, turns off, and a panel the app takes away while it is in its window: a panel that is there only while a task runs now shows where it was docked when the app makes it again. A panel that floated alone before it went still comes back to that window. `LayoutChanged` is raised as the panel goes back. A test that expected the panel to float after it returned should now expect it where it was docked.

#### 2026-11-21

- A `TbDockPanel` can ask before it closes and mark unsaved changes. `CanClose` (`Func<Task<bool>>`) is asked before the user closes the panel, by the tab's mark, Delete or Backspace, a middle click, Close in a menu or a test helper; returning false keeps the panel, its content and the focus. The app's own `Layout.Close` isn't asked. `Modified` shows a dot on the panel's tab or strip button (`data-part="modified"`, class `tb-dock__modified`, and `data-modified` on the tab or button), on a tab in the close mark's place until the pointer or the keyboard focus is on it, and describes it as "Unsaved changes" (`DockLabels.Modified`, `TbStrings.DockModified`). The Playwright helper's `CloseAsync` now waits until the dock has handled the close, where it waited for the tab to go.
- A `TbDockManager` panel that starts with a control is no longer a tab stop of its own, as a `TbTabs` panel already wasn't: Tab goes from the group's menu button straight to that control, one press fewer for every panel in a workspace. A panel that starts with text is still a stop. The dock's script decides, and sets such a panel's `tabindex` to `-1`, so the panel can still be focused from code. `FocusablePanels="TabPanelFocus.Always"` brings the stop back for every showing panel, and `Never` takes it from all. A browser test that pressed Tab to reach a panel that starts with a control, or expected `tabindex="0"` on one, needs updating; bUnit still sees `tabindex="0"`.
- `TbForm` knows when it is handling a submit. From the submit until `OnSubmit`, `OnValidSubmit` or `OnInvalidSubmit` finishes, each submit `TbButton`, `TbIconButton` or `TbFab` in the form shows a spinner and is marked busy, as with `Loading`, and a second submit is dropped. `@bind-IsSubmitting` lets the page follow it, and `ShowSubmitting="false"` leaves the buttons as they are. A page that sets `Loading` on its submit button from a flag of its own still works, and can drop the flag.
- More keys that a control uses now have their default prevented, so a `TbHotkey`, or an app's own key listener that skips events whose `defaultPrevented` is true, no longer also runs for them: Delete on a `TbChip` with a remove button (Backspace already was), Delete and Backspace on a `TbTabs` tab that can't close, a letter typed on a `TbMenu` item to jump to the next item that starts with it, the letters, and a Space mid-word, typed on a `TbSelect` to jump to an option, and Down Arrow in a tree select's filter box. What each key does is unchanged, except that a Space typed mid-word on a select no longer scrolls the page.
- `DockLayout.Retain(panels)` gives the layout with only those panel ids: any other leaves its group, its window, its strip and `Closed`, and isn't remembered. A layout keeps a place for every id it ever held, so one saved by an older version of an app carried the panels a newer version had removed or renamed, and dropping them meant rebuilding the layout by hand. Read the saved layout with `TryParse`, call `Retain` with the ids the app has now, then `Open` what must show.
- `TbDialogContentHost<TDialog, TResult>` shows a `TbDialogContent<TResult>` outside a dialog, such as in a `TbDockPanel`, a drawer or on the page. The content's `Dialog.CloseAsync(value)`, `Dialog.CancelAsync()` and `OnDismissAsync` work as in a dialog; the host gives the result through `OnClosed` and `Result`, takes the content's parameters through `Parameters` and `Update`, and its title through `@bind-Title`. Content used to throw "Open ... with IDialogService" anywhere but in a dialog the service opened.
- `TbDialogActions` no longer reaches past its container outside a dialog. Its negative margins and side padding, which carry the bar to a dialog's edges through the body's padding, now apply only inside a dialog's or a drawer's body (`.tb-dialog__body`); elsewhere the bar keeps within its container. Inside a dialog nothing changed.
- A `TbDockManager` keeps a way back to a panel that is in a browser window of its own. While a panel is away, a row above the strips and the groups (`data-part="away"`, class `tb-dock__away`, a `group` named "Panels in their own windows") has a menu button for it (`data-part="away-menu"`, with `data-panel`), named by the panel's title and described as "In its own browser window". Its menu has Show its window (`data-away="show"`), which brings the window to the front where the browser allows it, and Return to the dock (`data-away="return"`), which leaves the focus on the panel's tab. The page used to keep nothing for such a panel, so someone whose panel window was behind the page had no way to reach it from the keyboard. While the row shows, its height comes out of the dock's. `DockLabels` has `Away`, `AwayHint` and `ShowWindow` for the three new texts.
- `TbDockManager` has `PoppedOut`, the ids of the panels that show in browser windows of their own; `PoppedOutChanged`, raised when one goes to a window or comes back, and not when the browser refuses the window; and `ReturnAsync(panel)`, which brings one back from code.
- `TbDockPanel` has `AllowPopOut`, true by default. With the dock's `AllowPopOut` on, a panel whose own is false has no Open in new window in its group's menu or its tab's, and comes back to the dock if it is in a window of its own when the parameter turns false. Use it for a panel that has to stay on the page, such as one that holds an `<iframe>`. The test helpers' `PopOutAsync` now says "The panel \"Notes\" can't open in a window of its own: the dock's AllowPopOut is off, or the panel's is." whichever is off.
- Delete and Backspace now have their default prevented on a `TbDockManager` tab that can't close too, where the dock used to leave the key alone. The tab still doesn't close. An app's own shortcut for either key that skips events whose `defaultPrevented` is true, as `TbHotkey` does, no longer runs while the focus is on a dock tab.
- A load or a search that fails is now logged and counted. When a `TbDataGrid`'s `DataProvider` throws, for its rows or for an export, or a `TbTreeView`'s `LoadChildren`, or the `Search` of a `TbAutocomplete` or a `TbMentionInput`, the component logs a warning with the exception under its own category, such as `Trailblazor.TbDataGrid`. The message names the control by its `TelemetryName`, or else its label, as in "TbDataGrid jobs failed to load." A control with a `TelemetryName` also counts the failure in the new `trailblazor.control.failed` counter, with `trailblazor.action` set to `load` or `search`. The failure used to reach only `OnLoadFailed` or `OnSearchFailed`, so an app that bound neither never heard of it. Both are still raised, and a load or a search that was canceled or replaced is still neither logged nor counted. A `TbTreeView` also logs, at Debug, a row's click or toggle whose key no row has anymore, which it used to drop silently.
- An exception thrown while a component handles a call from its own script now goes to the renderer, as one from an event handler does: an `ErrorBoundary` around the component catches it, and Blazor logs it.
